# RepairSeal 科学性与论文闭环复核

复核日期：2026-11-27（UTC+8）。本复核以本次提供的项目为对象；下文明确区分原有记录、本次新执行和审稿判断。`paper/` 原稿不在本目录中直接修改。可精确应用于独立修订稿的 13 项修正见 `manuscript-corrections.json`。

## 一、总体判断

项目已经具有相当多的实现、真实来源、对照和失败记录。最重要的增量不是再积累几千次重复运行，而是把贡献、实现范围、证据范围和论文表述对齐，修掉能够被简单反例推翻的论证，并让真实补丁证据进入主论文。当前核心可成立的定位是：**在明确声明的有限修复契约下，比较接收者要返回的结果、事先获得的信息与已建立的状态，量化不同接收路径的计算，并报告有效边界和负结果。**

它尚不是任意 C 程序的自动正确性证明器；完整向量的擦除定理也不是关于所有证明证书的复杂性下界。把这两条范围写清楚不会削弱已有结果，反而使它们成为能够被审查的研究结论。

原工程中的 `RESULTS_UPDATE.md`、真实 Angelix 补丁研究、六个 signed 证书案例与源码对应记录已经提供了比原正文更强的经验支撑，但原稿仍说 signed 扩展只有完整域路径、仍把从标量片段走向真实补丁完全放到未来。这种版本错位会让审稿人无法判断哪一套结论对应哪一套实现。应保留历史原稿，把新证据纳入一份有明确版本的独立修订稿，而不是继续叠加未整合的报告。

## 二、本次实际找到并重现的问题

### 1. 轨迹优先诊断不是“最浅分支”，也不是输入顺序的细化

原稿 `paper/sections/contract.tex` 的 “Why Trace Order Precedes Input Order” 把字典序最小轨迹解释为最浅出错分支，并声称轨迹优先顺序细化数值输入顺序。两点均不由定义推出。

本次新写并实际运行 `trace_order_counterexample.py`，使用两个已获接纳的 unsigned 请求，输入均为 `{0,1}`。原程序和参照返回 `0`，候选对两个输入都返回错误值 `1`。条件分支只改变未被返回值使用的 scratch 变量。

| 同一候选的输入 | 执行轨迹 | 执行的条件数 | 观察 |
| --- | --- | ---: | --- |
| `0` | `[(0,1)]` | 1 | 返回错误值 `1` |
| `1` | `[(0,0),(1,1),(2,1)]` | 3 | 返回错误值 `1`，却被选为 canonical 反例 |

第二条轨迹的首事件较小，所以即使它更长、嵌套更深、输入数值也更大，字典序仍选中它。再把外层 guard 取反并交换两个分支，所有返回值保持不变，canonical 反例却变为输入 `0`。分支只修改 scratch，因此该顺序还不能证明所选分支具有缺陷因果意义。

本次结果为：**2 个请求、4 个独立具体解释器的输入观察、6 个完整接收结果，full/direct/demand 全部与具体解释器一致，零分歧。** 见 `trace-order-results/summary.json`。这两个是人工构造的机制反例，不能计作两个真实 bug，也不并入原 780 个请求。

这里不需要改变 canonical 算法。应删除错误的“最浅”“细化”和未经测量的维护者偏好说法，把排序说明为为了接收器可比较性而固定的约定。如果希望进一步声称方便维护者调试，需要独立的人类使用研究；当前没有这种研究。

### 2. 接受结果传递的充分条件被写成了充要条件

`paper/sections/introduction.tex` 说结果 “exactly when” 投影已覆盖时可以传递，正文定理实际证明的是充分授权条件。已有 420 个扩展中存在 328 个未获覆盖授权却仍完整验收通过的结果，因此不能把覆盖写成接受的必要条件。

应写成：投影覆盖时可以安全重用；覆盖失败表示没有重用结论，需要回退，并不表示候选错误。定理本身和实现的回退语义无需改变。证据位置：`paper/sections/guarantees.tex` 的 acceptance-under-covered-domain-change 命题，以及 `paper/sections/evaluation-results.tex` 的 RQ3。

### 3. 投影工作量证明中存在类型层面的表述错误

`paper/sections/guarantees.tex` 的 demand bound 证明说每个投影集合都包含于原域。若原域元素是四维向量、投影元素是二维向量，字面集合包含关系并不成立。正确理由是：从有限域到投影像的映射满射，所以投影像的基数不超过原域。结论不变；修正证明即可。

### 4. 有限穷举和测试之间被写出了不存在的能力分界

`paper/sections/discussion.tex` 声称契约能决定测试套件不能决定的东西。对于同一有限域、同一语义、同一判定谓词，穷举测试和完整直接求值能得到相同的布尔结论；现有研究的直接路径本来就在证明这一点。

真实补丁实验支持的是：**公开给定测试没有覆盖到这些失败输入；扩大的、明确声明的域发现了失败；得到的输入可以作为绑定请求的证据复核。** 把该输入补入普通测试也能发现输出不匹配。因此应把优势放在显式覆盖、定义性谓词、请求绑定和再检查，而不是给证书赋予超出直接语义求值的辨别能力。已有 `RESULTS_UPDATE.md` 对此已经比较准确，正文应与之对齐。

### 5. 未定义行为不能描述成“所有输入都返回正确值”

原讨论使用一个执行了未使用的除零语句的候选，随后说它在所有输入返回正确值且任何返回值比较都看不到错误。按照项目采用的 C 定义性模型，发生除零的执行没有定义好的 C 返回值；某个编译构建可能碰巧输出预期结果，也可能异常终止或产生其他行为。

正确结论是“观察到的输出相等不足以证明源程序定义良好”，而非“输出测试原则上不可能揭示该故障”。此修正依据 C11 委员会草案 N1570 §3.4.3 的未定义行为定义与 §6.5.5 的除法规则；官方来源见文末 [S1]。源码见证与具体构建的原生观察需要分开保留。

### 6. 从测试推导循环界限不能证明完整性

原讨论说存档测试给出了作者期望的循环界限。已观察测试至多给一个经验候选上界，不能恢复作者意图，也不能排除声明域中其他输入需要更多迭代。

若后续增加循环支持，必须在声明域上证明或检查展开充分性，或明确将超过界限的情况标记为 inconclusive。CBMC 的官方材料也把 unwinding assertions 用于检查展开充分性，见 [S2]。直接照测试最大迭代次数展开再返回接受，会破坏当前契约的含义。当前轮次不应把循环、数组和内存支持写成已经完成的扩展。

### 7. 完整向量的历史审计价值有合理用途，但缺乏比较证据

正文把完整记录描述为能在编译器、语料和批准者消失后继续证明过去接受了什么。这种论证遗漏两个条件。

首先，记录仍需要完整请求、源语义、codec 和相容的接收实现。自带 SHA-256 可以检测不匹配，不能单独证明由谁、在何时、以何种授权批准。其次，一个有版本的请求、结果收据和可信来源记录是更小的文档基线；完整向量额外保存的是中间断言，而不是唯一能保存历史结论的形式。

因此可以保留“支持重建时比较提交过的中间值”作为设计用途，不能把相对于所有收据方式的审计优势当作已测量结果。已有 1.6 倍接收时间和 23 倍大小比较回答的是成本，不是审计收益。

## 三、真实证据的价值和仍然存在的边界

下表中的数量来自输入项目的既有研究记录，不是本复核重新执行的外部实验。

| 证据层 | 既有记录支持的结论 | 不能推导的结论 |
| --- | --- | --- |
| 127 个公开 APR 补丁、67 份原源码 | 固定小型源码样本中确实存在 O0、O1、O2 失败 | 工业 C 补丁总体发生率，或三个诊断是从样本中发现的唯一完备分类 |
| 14 个补丁通过完整给定测试，11 个有额外域反例 | 全部提供的测试可能漏掉真实发布补丁的错误 | 任何测试方法都无法找到这些错误 |
| 6 个真实 APR 证书案例、5 个原始 subject、2 类题目 | 六个具体补丁贯通原源码、适配、模型、全域接收和单点反驳 | 六个独立工业 bug，或 signed 接收器已具有非空 preservation 区域 |
| signed frontend 接纳 223/7,806 个 source occurrence，对应 95/3,903 个 subject | 自动源接纳范围可量化且狭窄 | 数千个不支持来源也获得了正确性验证 |
| 完整接收器、direct、demand 一致 | 遍历、缓存、停止、诊断约定相容 | 三者共享的 frontend 没有建模错误 |
| 两编译器与具体解释器对照 | 降低这些已执行源码和输入上的对应风险 | 任意编译器、任意配置、任意输入的全局等价证明 |

数量可定位到 `RESULTS_UPDATE.md`、`artifact/experiments/real-patches/summary.json`、`artifact/experiments/introclass-certificates/README.md` 和 `artifact/experiments/natural-domains-review/summary.json`。不能把 source occurrence、源码身份、subject、候选、请求和题目混成一个“真实 bug 数”。

特别需要解释策略差别。source study 的操作性 R 由 original/reference 关系定义；signed 接收器固定 R=True。因此 smallest 某个见证在 taxonomy 中是 preservation failure，而 signed 证书的根名是 repair。这不是测量冲突，但不能写成 signed 证书已验证非平凡 O2。`src/int32_refutation.py` 只在一个确实存在于声明点集中的向量计算语义；请求构建、完整点集验证、成员检查仍有成本，所以 `checked_points=1` 不代表端到端工作与域大小无关。

“独立复核”也应精确到独立性的层级。第二套脚本、手写分支模型和另一个 compiler 是计算实现独立性，不是两位人类标注者，也不是完全独立的语法基础设施。现有报告明确零人工标注者，这一表述应保持。

## 四、创新性应如何表达

当前最有防御力的组合贡献是：一个明确的有限修复关系；固定 canonical 结果后的相同任务比较；区分完整值记录、单点见证和先前接受状态；以及由同一框架给出的正负实验结果。最弱的写法是把完整向量逐单元重算的事实外推成“一般证书没有用”，或断言此前没有任何工作匹配接收任务。

有三类近邻需要明确区分。

| 近邻 | 官方原始材料中的目标 | 对 RepairSeal 的正确比较方式 |
| --- | --- | --- |
| Poracle | 用户给 preservation condition，并用差分模糊测试发现违反保持条件的输入 [S3] | 对照输入契约和 refutation 目标；没有共同实现与预算实验时，不声称检测率或速度优于 Poracle |
| 正确性 witness 格式 | 交换 invariant，并要求规定对程序执行成立 [S4] | 这些 invariant 可以包含直接分析需要发现的信息；RepairSeal 的向量擦除定理不适用到所有 invariant 证书 |
| Witness validator 研究 | 研究 validator 是否确认无效 witness，并保留原始结果 [S5] | 支持把格式、绑定和错误接受纳入实验；不能仅凭两个工具返回相同布尔值就认定全部注释被真正消费 |

这是一轮有针对性的原始来源核对，不是系统文献综述。没有依据将项目称为“第一次”解决所有这些问题。13 项修正中的 novelty 段落给出了更窄、更能被现有实验支持的英文表达。

## 五、怎样把这轮工作做成闭环

本轮合理的完成标准是：保留历史证据；给出独立修订稿；把新增真实补丁研究纳入问题、方法、结果与限制；把上述错误主张替换为准确主张；保存新运行的实际记录；检查修订文本与数据路径、图表、参考文献和编译结果一致。达到这些条件，可以说“这轮可执行补强已完成”。不能据此保证 TOSEM 接收，或宣称工业规模验证问题已经解决。

仍真正值得后续投入的研究只能按明确新结论立项，而非增加样本次数：

1. **扩大自然代码结构覆盖。** 若增加循环，交付应包含声明域上的展开充分性检查、超界的 inconclusive 行为、原始代码和独立 native 对照；否则即使新增一百个循环程序也不构成可靠支持。
2. **测量真实接收者用途。** 若主张审计或调试价值，比较完整向量与请求加收据这类最小基线，定义可衡量的任务；当前没有开发者研究，不能用脚本一致率代替。
3. **真正移除模型共因风险。** 在一批预先冻结的新来源上，对原始 C、规范化 C、独立语义实现和编译观察逐项对照；已发现失败后定向选取的六案例继续作为机制研究报告，不伪装成无偏泛化样本。

以上三条并非要求本轮仓促实现任意 C、工业部署或人工研究。它们标识了当前结论的外缘，避免把“工作量已经很大”误写成“所有外部有效性问题已经关闭”。

## 七、本轮新增序类型研究的后续独立复核

在上述主稿审查后，项目又新增了 `real-validation/order_types.py` 与 `proof.md`。这项工作尝试把六个真实候选中只有比较、复制和有限分支的计算，按相等关系及大小顺序压缩成有限弱序类型，从而对**这一严格限定的计算片段**给出所有 int32 输入上的故障类别分析。它没有扩大 RepairSeal 原有有限证书域，也没有覆盖任意 C。

独立审查发现新模块初稿的两个源码接纳问题：去除 stdio 头之后，曾允许 `EOF` 这类宏名称作为局部变量；曾用 Python 字符串解码解释 C 的 I/O 格式，导致 `\\x25d` 的不同十六进制词法规则混淆。两者都可能使新模块接纳并非所声称语义的 C 文本。它们没有出现在本次固定的 13 份源码中，但会破坏泛化到“所有接纳的比较/复制程序”的源码边界。开发者已改为保守的局部变量名约束和字面 I/O 格式规则，并保留首轮记录后重跑绑定新代码的实验；没有改写旧运行的源码指纹。

修正后，本复核另用递归有序集合划分生成类别，而不是调用研究中的笛卡尔 rank generator。两种生成方式在 1、2、3、4 个输入上分别得到完全相同的 1、3、13、75 类；全部 13 份固定规范化源的 417 个 source/class 执行通过。另有 12 个针对数据常量、零值判断、隐式 truthiness、算术、cast、循环、宏名、C/Python 字符串差异、未初始化路径与多输出路径的边界检查符合预期。实测记录及被审代码哈希见 `independent-order-review.json`。

数学结论也作了单独检查：每个已初始化变量保持为某个输入坐标的副本；比较只依赖输入的全序与相等类；短路逻辑维持相同求值路径；有限语句归纳维持相同分支、初始化及输出坐标。因此，在**所有类别都通过已初始化读取与恰好一次输出检查**、输入是成功转换的 int32 十进制值、I/O 与平台前提成立时，弱序枚举足以判定整个相关 int32 输入空间的输出行为。没有数据算术，故此推导不依赖有限样本上未观察到溢出，也不能转用于含算术的程序。

本次复核结论为：在写明的窄 profile 与 I/O 前提内，没有发现剩余的具体错误；该归约具有清楚的归纳论证和独立枚举核验。这是计算复核，不是人工专家签名、定理证明器证明、又一轮 native 实验或“独立 bug 数”的增加。原始和规范化 C 的对应关系仍按固定源身份、已有结构审查及本轮原生边界执行提供证据。不同结构补丁可能属于同一输出行为类，应利用这种等价压缩报告样本多样性，而不是把重复行为包装为更多独立证据。
